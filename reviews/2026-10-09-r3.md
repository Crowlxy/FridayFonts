## 指摘

### [P1] Sans Light の漢字で字形が壊れている（Sans UI Light も同じ）

- 症状：Regular〜Bold にある画が Light だけ欠ける、黒い楔（くさび）状の塗りつぶしが出る、小さなとげが出る、のいずれか。FreeType（PIL）でフォントファイルを直接描いて確認した。独自の描画ではない。
- **目視で壊れを確認した字（18 字）**
  - 画が欠ける：共（八の右のはらい）、題（頁の右のはらい）、罘（U+7F58）
  - 楔の塗りつぶし・かたまり：武・昆・廃・戯（U+622F）・魃・茈（U+8308）・釖（U+91D6）・緝・簒・蘆（U+85D8）・槨（U+69E8）・U+8DAF
  - 小さなとげ：慮・唄・噏（U+55CC）
  - 見本：[共・題・慮](../work/claude-review-20261009/view-light-common.png)、[題を Light・Regular・Medium で](../work/claude-review-20261009/view-dai.png)、[Light 5段比較 1](../work/claude-review-20261009/view-light-1.png)、[同 2](../work/claude-review-20261009/view-light-2.png)、[同 3](../work/claude-review-20261009/view-light-mid.png)、[魃を 2.5・3.0 で](../work/claude-review-20261009/view-9B43-pil.png)
  - 目視したが、他の2ウェイトと見比べてもはっきりした壊れを認めなかった字：圓（U+5713）、驀（U+9A40）。目視した字は、この2字を含めて約 25 字。
- **検出のみの候補（75 字）**：cmap にある CJK 字 10,021 字を Light と Regular で比べ、差が大きい字を数えた（基準：差の連結面積が 160 px/em で 8 px² 以上）。75 字のうち、上の目視済み 18 字と圓・驀を除く約 55 字は、見ていない。誤検出を含みうる。JIS 第一水準は 17 字（共・題・武・昆・廃・戯・慮・唄 は目視済み。厩・捷・斌・毘・疋・蔽・襲・輯 ほかは未目視）。一覧は [light-defects.txt](../work/claude-review-20261009/light-defects.txt)。
- Sans UI Light も同じ：同じ検査を UI で実行すると、Light と Regular の差が基準以上の字は 74 字で、Sans と 73 字が共通（差は基準の境にある 3 字：婿・澀・美）。目視は共・題・慮 のみ。
- 3.0 の変更で生じたものではない：魃（U+9B43）は 2.5 の Light と 3.0 の Light で面積・外接が完全に一致する。共・題・慮も 2.5 の Light で同じ状態を確認した。つまり**公開済みの 2.5 Light から壊れている**。
- Light 以外は 0 件：Regular↔Medium、Medium↔SemiBold、SemiBold↔Bold の3組は、12 px² 以上で 0 字（Sans・UI とも）。cmap にない異体字 1,806 字（全ウェイト）は 24 字が基準を超えた。目視したローマ数字 7 字は、幅の違いによる誤検出で壊れではなかった。残り 17 字（記号・引用符の異体など）は目視していない。
- なぜ既存の検査で見えないか：`verify_sans_30.py` は 2.5 と 3.0 を比べる。2.5 側が壊れていれば一致して合格する。`render_check.py` は「空描画・縦つぶれ」しか見ない。
- 原因：検証していない。3.0 の処理は関係しない、というところまでしか確認できていない。
- 修正案：Light の壊れた字の輪郭を作り直す（ソースの Light から再生成するか、Regular と Medium からの補間）。対象は目視済みの 18 字と、候補のうち目視で壊れと確認できた字。作り直したら、隣り合うウェイトの輪郭がどれだけ離れているかの検査を `verify_sans_30.py` に入れる。README の「Light / SemiBold は Windows 実機での確認がまだ」という注記とは別に、「Light に壊れた字がある」と明記するか、直るまで Light を外す判断が要る。
- 検査の限界：隣のウェイトと形が大きく違う字を拾う検査。全ウェイトで同じように壊れた字は拾えない。

### [P2] GDI 系アプリの行の高さが 1.87 em になる（Sans）

- `usWinAscent/Descent` は Sans が 2660/1083（1.87 em）、UI が 2634/1072（1.85 em）。hhea・typo は Sans 1.50 em、UI 1.254 em。Win 値を使う GDI 系のアプリでは、既定の行間が hhea の約 1.25 倍（Sans）・約 1.5 倍（UI）になりうる。どのアプリが Win 値を使うか（Office・メモ帳など）は確認していない。この書体は USE_TYPO_METRICS が立っているので、DirectWrite 系は Typo 値を使う可能性が高い。
- 原因：全字形を覆う方針のため、縦書き用のくり返し記号 〱〲（U+3031・U+3032）が決めている。この2字は上端 1.32 em、下端 −0.54 em まで伸びる。それ以外は、アクセント付きラテン（Ǻ、上端 1.16 em）と結合記号（下端 −0.33 em）。この2字を除くと、Win 値は約 1.49 em になる。
- 比較（この PC の Win 値の合計）：Yu Gothic 1.29 em、Segoe UI 1.33 em、Meiryo 1.50 em。
- README に「RC3 から続く制限」と書いてある既知の事項。ただ、AGENTS.md の「どの端末でも美しいか」という基準では、Win 値を使うアプリで本文が間延びして見える可能性は指摘に値する（実機では未確認）。〱〲 を GDI で欠けさせるか、1.87 em を受け入れるかは設計判断なので、ユーザーが決める。
- Mono 5.0.1 の Win 値も同じ方針で 1.495 em。README に記載済み。

### [P2] Mono Light の ½（U+00BD）の輪郭が壊れている

- 分母の 2 が、小さな「∠」のような断片になっている。Regular・Medium・SemiBold・Bold と Italic 系（LightItalic を含む）は正常。[見本](../work/claude-review-20261009/view-mono-frac.png)。
- **ヒントの壊れではなく、輪郭の壊れ**：ヒントなしの輪郭だけを描いても同じ断片になる。5.0 の Light でも、5.0.1 の Light でも、12・16・24・48・150 px で同じ（[比較](../work/claude-review-20261009/view-mono-half-hinting.png)）。5.0 と 5.0.1 で座標は同一なので、5.0.1 の再ヒントによる回帰ではない。公開済みの 5.0 から壊れていた。この字形は 3 輪郭（点数 12・13・4）で、分母の輪郭が 4 点しかない。
- 隣のウェイトとの差を同じ方法で、Mono 全 10 スタイル × 1,061 字について調べた。他に壊れた字はなかった（Italic の差はスラントの違い）。ただし、この比較は FreeType のヒント適用後の描画で、ヒントの壊れを拾う目的の検査ではない。
- 修正案：Light の ½ の輪郭を、Regular・Medium の ½ を元に作り直す。

### [P3] Medium → SemiBold の太さの段差が、密度の高い漢字で潰れている

- 密度対応の減量が原因とみられる（検証は「段差の数値の確認」まで）。漢字 9,322 字で、Medium→SemiBold の面積の増え方が 2.5 の半分未満の字が 241 字（2.6 %）。このうち 14 字は SemiBold のほうが Medium より面積が小さい：幤 惸 齟 樗 鷟 渹 齬 埶 濟 齰 責 葊 辯 浸。2.5 では +5.8〜+8.5 % あった段差が、−3.8〜−0.1 % になる。
- 他の組（Light→Regular、Regular→Medium、SemiBold→Bold）で逆転はない。差は最大 3.8 % の面積で、目に見えるかは未確認。

### [P3] 2.5 の輪郭のまま残る字が 15 字ある（太らせも角の面取りも受けていない）

- 2.5 と面積が完全に一致する字が、Light 4・Regular 5・Medium 3・SemiBold 1・Bold 2 字ある（例：瀬 U+7027、臘 U+81D8、繭 U+7E6D 〈Bold〉）。輪郭数が変わる既知の字と多くが重なる（重なりの全数照合はしていない）。README の「面積と外観は変わっていません」は事実だが、「他の字は面積が 2.5 の約 1.02〜1.09 倍なのに、この字だけ 1.00 倍で、角が尖ったまま」という意味でもある。輪郭数が変わる字は `KNOWN_CONTOUR_CHANGES` に記録済みで、`verify_sans_30.py` は終了コード 0。

### [P3] ≒（U+2252）が Sans にない

- JIS X 0208 の 6,879 字のうち、Friday Sans に無いのはこの1字だけ（2.5 も同じ、Web 用の軽量版も同じ）。アプリの代替フォントで表示される。

### [P3] 文書・配布物

- ルート README が 3.0 の実態と合っていない：
  - 「Sans UI は Sans より字面を約5%小さく」→ 実測 0.896 対 0.887 で約 1 %（Sans の README 自身が書いている値）
  - 「漢字にChlorophytumでヒントを付ける」→ 3.0 はヒントを全部外している
  - トップの見本画像が `releases/sans-2.5/` のもの
- Sans の README：「Regular で約 1,700 字が減量対象」は、`build-log.json` の Regular（885 字）と合わない。密度対応前の数字が残っているとみられる。
- 配布 ZIP の `reports/` に、密度対応前の `audit-unhinted.*`・`weights-proof-*`・比較画像が入っている（README に明記済み）。
- `FridayMono-5.0.1/` の `SHA256SUMS.txt` は CRLF 改行。macOS・Linux で `sha256sum -c SHA256SUMS.txt` を実行すると、全項目が「No such file」で失敗する（`\r` が名前に付くため）。Sans のほうは LF。
- ss01〜ss08 の FeatureParams が参照する name ID が name テーブルにない（検証スクリプトの警告は 276〜297 の 22 個。cv 系も同様とみられるが未確認。2.5 も同じ）。フォントの機能名がアプリに出ない程度で、字は表示される。
- `FridayMono-5.0/`・`FridayMono-5.0.1/`・`FridaySans-3.0/`（展開済みフォルダ）と `AGENTS.md` が未追跡で、`.gitignore` にない。`*.ttf`・`*.woff2` は無視されるが、README・画像・SHA256SUMS・CSS は `git add -A` で入る。削除はしていない。

## 検査して問題がなかったこと

- **配布物の整合**：Sans ZIP の内部 `SHA256SUMS.txt` 44 項目、Mono ZIP の 93 項目が全て一致（Mono は CR を除いて照合）。ZIP 内の TTF 10 本は展開済みフォルダと同一。外部 `.sha256` も一致。
- **upem 2000 への換算漏れ**：なし。hhea・OS/2（Win・Typo・x高さ・キャップ高・上付き下付き・取り消し線）・post の下線・vhea・head の外接が、全10本で Sans は 2.0 倍、UI は 2000/1010（1.9802 倍）。`gasp` は version 1・0x000A。`fpgm`・`prep`・`cvt ` は無く、`maxp` の命令サイズは 0。
- **GPOS・GSUB の中身**：HarfBuzz で 2.5 と 3.0 を実際に組んで、字形列と位置（送り・オフセット）を換算して比べた。ラテン 2 字の全組合せ 5,476、結合濁点 45、かな・約物 約 230 字（横組み・縦組みの `vert`）、漢字 400 字、混在文 5 文 × 16 機能（palt・halt・fwid・hwid・jp78・jp90・ss01・tnum・zero・ruby・kern・liga・calt ほか）。10 本全てで不一致 0（許容 1.6 units）。検査が空振りでないことは、`Wa` のカーニングと縦組みの offset が実際に出ることで確認した。
- **Win 値の被覆**：Sans 全 10 本で、cmap にない字形を含む全字形の輪郭（BoundsPen の実際の外接）が `usWinAscent/Descent` に収まる。余裕は Bold で 2 units（2658.1 対 2660）。lsb は全字形で xMin と一致。Mono 5.0.1 も全 10 スタイル・全字形が収まる（BoldItalic は 1164.0 対 1164 で余裕 0）。
- **`verify_sans_30.py`**：ZIP 内の TTF で実行し、終了コード 0（`OK: no problems`）。name ID 276〜297 の警告が出る（上記）。
- **`render_check.py`**：ZIP 内の TTF 10 本 × 15,212 字 × 9・12・16・24 px で、エラー 0・空描画 0・つぶれ 0。
- **局所的な過剰・欠落**：5 ウェイト × 16,720 字形について、3.0 の輪郭を 2.5 の輪郭から `e + 1.5` units だけ広げた範囲と比べた。面取りの三角形より大きい欠け（0.9 dv² 超）は 0。範囲外の新しいインクは、凹角の丸め（フィレット）による端の細い線のみ（目視：[冣・鍛・碕](../work/claude-review-20261009/view-excess-light.png)）。pathops が演算に失敗して数値が使えない字が 7 字（面積の整合から判定）あり、これは検査の対象外。
- **輪郭数が変わる既知の 15 字**：目視で、隙間の埋まり・欠けは見えない（[1](../work/claude-review-20261009/view-known-1.png)・[2](../work/claude-review-20261009/view-known-2.png)）。ただし魃（Light）は 2.5 から壊れている（[P1]）。
- **WOFF2**：全字形版 10 本は、TTF と cmap・全字形の座標・hmtx・Win 値が一致（fontTools で復号して比較。ブラウザの検証器ではない）。軽量版は各 8,414 字で、ASCII・Latin-1 と JIS X 0208 を含む（U+2252 以外）。`vert` を保持。
- **Mono 5.0.1 と 5.0**：全 10 スタイルで、全字形の座標・フラグ・hmtx・cmap が同一。差は OS/2（Win 値）・name・head・`cvt `・`glyf` の命令・`loca` のみ（ヒントの再生成による）。
- **OS/2 の文字範囲・コードページ**：Sans の 10 本全てで 2.5 と同じ（コードページ 932 を含む）。`macStyle`・`fsSelection`・名前 ID 1/2/16/17 は Light〜Bold で規則どおり。
